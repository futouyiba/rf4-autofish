## 1. 为什么必须做（今天的事故都能归到三类）

| 事故 | 缺的是什么 |
|---|---|
| 15:48 拉鱼到一半松手，鱼把线拉出 200 米 | 没有"线没收回"这个**状态事实**，只有"计时器到点" |
| 16:47 `ring=-1` 被当成临岸 → 连套 3 次网 → 松手 | "**未知**"没有独立状态，被迫在 是/否 里二选一 |
| 16:15 抄网掏不出来 | 按键**不变量**没有唯一 owner（谁该按住 F5 没人管） |
| 45 秒计时器不重置 | 计时器挂在函数里，跨阶段**泄漏** |
| 重启后"以为 17 实际 29"，顶满断线 | 状态只活在进程内存，**无法从外界重新确认** |
| 每条鱼开头回 17 vs 保留 29 反复摇摆 | 两条代码路径对同一状态各自解释 |

归成三类根因：

1. **计时器 / 计数器没有归属** → 跨阶段泄漏
2. **按键不变量没有唯一 owner** → 谁松的、谁忘了按，查不出来
3. **"未知"被当成确定值** → 把"读不出来"当成"读到了某个值"

状态机不是为了代码漂亮，是为了让这三类 bug **结构性地消失**。

## 3. 启动探针（回答问题 2）

`probe_state()` 采样 3 帧（间隔 0.15s），**按"最确定 → 最不确定"排序**判定：

```
0. 物理按键检查：F5 / F6 已被按下？
     → 是：判定「人工接管中」或「残留按键」
        → 不接管、不产生任何输入，只观察 + 上报
1. 「确定」按钮连续 2 帧成立            → S9_MODAL
2. 入护按钮 / 结算框存在                → S8_SETTLE
3. 鱼图标连续 2 帧存在
     ring >= 0.98                      → S6_LAND
     否则                               → S5_FIGHT
4. bar 有色（level > 0）               → S5_FIGHT
5. ring 可读 或 力度条区域有绘制        → S4_WAIT_BITE
6. 三件套全暗                          → S2_READY（窗口在前台）/ S1_MENU
7. 以上都不成立                         → S0_UNKNOWN
```

铁律：**`S0_UNKNOWN` 与 `S1_MENU` 一律不产生任何键鼠输入**，只打印各判据读数 + 上报截图。宁可不动，不可乱动——今天所有"事故级"问题都发生在"判据不确定却被当成确定"的时刻。

> 判据 3 的"连续 2 帧"是必须的：单帧误读会把 `S4_WAIT_BITE` 误判成 `S5_FIGHT`，一上来就按住左右键（把竿抽回来）。

### 3.1 为什么不"先观察 2 秒再接管"（2026-11-04 17:17）

盲等 2 秒几乎没有额外的**视觉**信息——判据 3 已要求"连续 2 帧"，本身就在防单帧误判；而"鱼还在不在"这 2 秒能给的信息，用 3 帧采样就已经拿到。

真正需要解决的不是"等多久"，而是**按键所有权**。

### 3.2 人和脚本一起按可以吗？

短时间内可能看起来能用，但**不能作为安全假设**：Windows 不会给"人按了一次"和"脚本按了一次"维护两份引用计数。同一个 F5/F6 最终只有一个全局 up/down 状态；任意一方发送 `keyUp`，游戏都可能看到松开。

所以这组事件不可靠：

```
人工 keyDown(F5)
脚本 keyDown(F5)   # 不会变成"按住两份"
脚本 keyUp(F5)     # 可能把人工仍压着的 F5 也变成释放态
```

`GetAsyncKeyState` 也只能回答"此刻系统认为键是否按下"，不能回答是谁按的。正确命名应是 `EXTERNAL_OR_UNKNOWN_HOLD`，不能直接叫"人工接管"。

MVP 的安全策略：

1. 冷启动检测到 F5/F6 已按下 → 状态识别继续、**不发送该键的 keyUp**；UI 显示"外部按键占用"。
2. 用户选择接管 → 先提示用户松开实体键；连续确认全部为 up 后，bot 再发自己的 keyDown。
3. "强制接管"作为高级动作：明确提示它会先 keyUp 再 keyDown，可能造成短暂松键。
4. bot 自己运行期间，按键全部由 `InputArbiter` 管；业务代码不能直接 keyDown/keyUp。

后续若真要区分人工/注入事件，可用 `WH_KEYBOARD_LL` + `LLKHF_INJECTED` 观察事件来源，但它仍不能提供引用计数，只适合检测"人工开始介入"并切到手动模式。

## 4. 分场景初始化（回答问题 3）

### 4.1 核心原则：校准只能朝"安全端"饱和

摩擦片调**小** → 钓具承受力变小 → **不可能断线**；调**大** → 可能直接断线，而且屏幕上没有档位读数可以事后发现。

由此得到一条铁律：

> **任何"档位未知"的时刻，绝对校准只能朝安全端（向下）饱和。**
> 向上饱和（滚满 30 再退回）**只允许在线上无鱼时做**。

这就是你说的"鱼挂着不能 up 30 再 down 13，只能 down 到 0"的本质。它的价值不止是防断线：**向下饱和的结果是确定的**（多滚几格只是无效动作，档位到底就不再变），而向上饱和过一次终点就断线了。

### 4.2 初始化矩阵

| 启动时状态 | 摩擦片初始化 | 其他初始化 |
|---|---|---|
| `S2_READY` | **危险校准**（up 30 → down 13 到 17），线上无鱼，安全 | 复位计时器、清弹窗、抛竿 |
| `S3_CASTING` | 不动 | 等落水 |
| `S4_WAIT_BITE` | **安全校准**（down 30 → up 16 到 17）；线上无鱼但已抛出，没必要冒顶格风险 | 复位计时器、等口 |
| `S5_FIGHT` | **绝不 up 30**。先读力度条：已在 2 档 → **完全不动**；在 1 档 → **down 饱和到 0，再 up 16 到 17**；在 3 档红 → **先降档救急**，校准之后再说 | 按住 F5+F6 |
| `S6_LAND` / `S7_NET` | **不动**（此刻调档无意义，且多一次风险动作） | 按 §7 的临岸流程 |
| `S8_SETTLE` / `S9_MODAL` | 不动，先处理界面 | — |
| `S0_UNKNOWN` | 不动 | 上报 |

### 4.3 "down 到 0 再 up 17" 的落地

操作序列（安全校准）：

```
1. 向下滚 30 格（> 最大档位差，保证到底；多滚只是无效动作）
2. 向上滚 16 格 → 17 档
3. 记账 cur=17, calibrated=True, 落盘
耗时 ≈ 46 格 × 55ms ≈ 2.5 秒
```

**代价**：这 2.5 秒里摩擦一直在低档，鱼会往外跑一点线（不会断线）。可接受，但要尽量少做。

### 4.4 `S5_FIGHT` 初始化：down 饱和 → up 到 17（定稿）

```
1. 向下滚 30 格（保证到底；多滚是无效动作，安全）
2. 向上滚 16 格 → 17 档
3. 记账 cur=17, calibrated=True, 落盘
4. 交给动态控制器（它自己按力度条升降，且受 29 档上限约束）
```

不用"边升边看力度条、到了 2 档就停"那种写法——理由见 §4.5。

### 4.5 数字与色带的分工（2026-11-04 17:17 玩家纠正）

我原先提过"搏鱼时档位数字没有意义，只按力度条闭环往上加"。**这是错的**，玩家指出：

> 如果到了 29 还在往上调，就容易断线了。

两个量各自只能回答一个问题，缺一不可：

| 量 | 能回答 | 不能回答 |
|---|---|---|
| **档位数字**（`_fric["cur"]`） | **还能往上调几格才安全**（29 是硬顶） | 现在负载够不够 |
| **力度条色带** | **该往哪边调、到了没有** | 还能往上调多少 |

- 只有数字没有色带 → 不知道该调多少（早期"永远停在 17"的阶段）
- 只有色带没有数字 → 会一路顶到 30 断线（尤其小鱼、低阻钓组：力度条长期停在 1 档，
  按色带闭环就会无限升档，而这恰恰是之前"档位总爬到 29"的真相）

所以铁律：

> **升档受数字硬约束（≤ 29），升/降的方向与达标由色带判断。**

到 29 且色带仍是 1 档 → **接受现状，不再升**（说明这条鱼/这套钓组的摩阻就这么大，已经到极限）。
这一点写进 `_rise_target()` 的语义里，不改。

## 5. 按键不变量（唯一 owner）

状态机持有 `keys(state) -> set` 的声明式不变量，每次迁移后做一次 reconcile：

```
期望按住集合  vs  当前实际按住集合
  → 多的松开、少的按下；只动差集
```

这直接消灭今天那类 bug（`_both_up` 绕过 `mouse_pressed` 记账、抄网前忘了松 F5）。**没有任何业务代码可以直接按键**，只能改状态。

## 6. 计时器 / 计数器归属状态

| 计时器 | 归属状态 | 生命周期 |
|---|---|---|
| 收线 45s 超时 | `S4_WAIT_BITE` → 进入时创建 | 退出即销毁 |
| 无张力 idle 15s | `S5_FIGHT` | 同上 |
| 临岸宽限 8s | `S6_LAND` | 同上 |
| 抄网动作/等待 | `S7_NET` | 退出即销毁；失败保持 NET + F6 |
| 弹窗连点计数 | `S9_MODAL` | 同上 |

**进入状态时创建、退出时销毁**——45 秒计时器泄漏那类 bug 从结构上不可能再出现。

## 7. 关键迁移与 guard

| 迁移 | guard |
|---|---|
| `S4→S5` | 鱼图标连续 2 帧 |
| `S5→S6` | ring 连续 3 帧 ≥ `ring_min`（默认 0.98：0.973 不 LAND，0.985 连续 3 帧才 LAND；**ring<0 → 永不迁移**） |

### 8.2 2026-11-05 抄网正式链路（F7；98 入 / 90 出）

用户实机确认：
- 真正“掏网/收网”键是 **F7**。旧 `PageDown` 会放竿/切装备，必须停用。
- 进入 LAND/NET 的 90% 门槛偏低，默认改为 **0.98**（0.973 不 LAND；0.985
  连续 3 帧才 LAND）。NET 退出阈值独立保留 **0.90**：0.89 连续 3 帧收网，
  形成明确的 **98 入 / 90 出** 回差。
- 上一轮实机：部署与收网注入都成功发送，但鱼未进入鱼护，最终判 **LOST**；
  这可证明“指令发出”，不能写成“收获”或“入护验收通过”。

实现：

- `FightMachine` 新增 `NetState.STOWED/DEPLOYED/UNKNOWN` 与
  `net_retract_action`；`RuntimeCallbacks` → `Bridge` 全接线。
- Bridge 统一 `_net_toggle(reason)`：同一 arbiter 发一次 `f7 down/up`，
  保持 F6、绝不按 F5；可取消、动作前检查前台恢复、`finally` 释放 F7；
  掏网/收网分别记 `deploy` / `retract` 日志。
- **修饰键保护**：F7 是裸键；Ctrl/Alt/Shift 任一被物理按住时不发（会撞
  `Ctrl+Alt+Shift+F7` 恢复热键），明确报 `net_modifier_held` 并只读阻塞，
  绝不替用户松键。全局恢复热键本身不改。
- 初始 `STOWED` 只用于正常新钓鱼会话；中途接管 `UNKNOWN`，禁止盲 toggle。
  掏网回调成功才 `DEPLOYED`。NET 中新鲜有效帧 ring 连续 3 帧低于
  `net_exit_ring`（默认 0.90）触发收网；成功后等待 `net_retract_anim`
  （1.2s，stop 可取消）再 `STOWED` 并回 FIGHT 补按 F5。
- 部分动作失败 → `UNKNOWN` + fault，保持 F6，不恢复 F5、不重复盲 toggle；
  `stop` 可释放。回调缺失时 LAND 保持双键，绝不跳过收网直接按 F5。
- 捕获强确认优先；`None/NaN/失焦/过时/重复` 帧不算低环且中断连续计数。
  收网后重新累计 3 帧 + 8s（不继承旧计时），并用 `net_cooldown=5s` 抑制振荡。
- `NET` 无总体放弃超时；`net_window` 只保留一次性提醒。
- 单源配置：`RF4_AUTO_NET=1` 仅供人工验收，默认 False；Bridge gate 与
  `FightConfig` 同源，不一致在进入 NET/松 F5 前 preflight 失败。
- 计时：`fish_elapsed` 从确认中鱼（`hooked_since`）起算；`cast_elapsed`
  保留从抛竿起算。状态迁移日志带 monotonic + wall（datetime）与
  ring/fish/tier、原因，不逐 tick 刷新。
- legacy `rf4s_adapter.net_toggle()` / `_net_action` 的抄网常量与直接注入
  也已统一引用 `NET_KEY="f7"`；`bot_ctl release` 仍保留 `pagedown`，仅用于
  清理旧版本可能残留的按键，不作为正式动作。

### 8.3 2026-11-05 线杯圆环自适应亮度（夜间满环不再误判）

**指示器位置**：底部状态图标排的第 2 个，与 `static/*/wheel.png` 同形；
外圈圆环即“线杯上还剩多少线”，满环 = 线基本都在线杯上（鱼近），环掉下来 = 线被拉出（鱼远）。

**旧实现为什么错**：同一帧实测三个相邻状态图标的环峰值分别是 **109 / 178 / 104**。
旧代码把“点亮”写死成 `>=180`，于是夜间/HUD 变暗时满环峰值 178 被整圈判成
“图标没画出来” → `ring=None`（实机已出现）。所有依赖它的判断随之失效：
临岸不迁移、收网不触发、状态卡在搏鱼里出不来。

**新判据**（`autofish_ring.py`，纯像素、无 IO、无输入；adapter 与
`autofish_observation` 共用同一实现，不再各存一套常量）：

1. `peak < 60` → `icon_not_drawn`（图标真没绘制/被遮挡），返回 `None` 而非 0；
2. 否则取该帧峰值按比例判每个角度：`v >= peak*0.68` 记为点亮，步长 2°；
3. 结构判据：区域均值 `>= peak*0.85` 说明是平坦色块（均匀灰/纯白盘），
   同样判 `icon_not_drawn`，避免比例法把背景噪声算成满环；
4. 区域均值 `<20` 直接判 `hud_dark`。

结果：同一满环在 178 与 255 亮度下都读成接近 1.0；`None` 只表示不可读，
语义上既不等于“0% 线”也不等于“临岸”，沿用 §7 的“未知不迁移”约定。

**验证口径**：真实截图满环 0.983；全黑 `hud_dark`；均匀灰、纯白盘
`icon_not_drawn`；合成 178 满环 ≥0.95、半环约 0.5。进入阈值 0.98 与
退出阈值 0.90 不变，本改动只修“读数”，不改控制律。

## 9. 实施顺序（复审后修订）

原计划把"状态机"、"按键 reconcile"、"计时器清理"拆得太开，会产生一个危险的中间版本：新状态机和旧 `hold_keys/_both_down/抄网代码` 同时拥有 F5/F6。修订为：

| 阶段 | 内容 | 验收标准 | 回滚 |
|---|---|---|---|
| 0 | **行为基线 + 输入语义实测**：同帧记录视觉、全量按键事件、`GetAsyncKeyState`；安全场景实测“人按 + bot 按 + bot 松” | 明确本机 RF4 对重复按键的实际行为；不改变钓鱼控制 | 关诊断开关 |
| 1 | **同帧 observation + shadow 状态推断**：只推断不控制 | 一整条鱼状态序列与肉眼一致；危险误判为 0 | 关 shadow observer |
| 2 | **最小状态机 + 唯一 InputArbiter + 状态局部计时器**，先接管 FIGHT/LAND/NET | 业务代码不再直接操作 F5/F6；FIGHT→LAND 不松键；LAND→NET 只松 F5；退出状态后旧计时器不能触发 | `AUTOFISH_STATE_MACHINE=0` 回 legacy |
| 3 | **启动探针 + ControlMode + 摩擦安全初始化** | FIGHT 未知档位严格 down30→up16；校准期间控制器冻结；29 硬顶 | 关启动接管开关 |
| 4 | **迁移完整生命周期**：READY/CASTING/WAIT/FIGHT/LAND/NET/SETTLE/MODAL | 可在任意已识别画面启动；UNKNOWN 零输入 | 按整条鱼切回 legacy |
| 5 | **独立 UI + IPC** | 杀 UI 不影响 bot；UI 不抢焦点；优雅停止可用 | UI 可选，不启动即可 |

当前落地：阶段 1–5 的代码与离线测试已完成；阶段 0 的“人按 + bot 按 + bot 松”
实机输入语义仍没有独立结论记录。阶段 5 的 UI 已实现为独立进程，关闭不影响后台。
实机验收仍未通过入护：上一轮部署/收网发送成功，但鱼未进入鱼护，判 **LOST**；
legacy 只有“钓到过小鱼”的历史记录，均不能称生产可用。

### 9.1 关键验收用例

- `ring=None` 永不进入 LAND/NET；`ring>=0.98` 连续 3 帧才进入 LAND
  （0.973 不 LAND；0.985 连续 3 帧 LAND）。
- `cur=29 + 1档色` 不升；`cur=28 + 1档色` 最多到 29；2 档色不动；红事件正常降。
- `FIGHT + 档位未知`：滚轮序列严格为 down 30、up 16；任何一步失败都不能写 `calibrated=True`。
- 校准与动态控制器不能并发。
- `FIGHT -> LAND` 期望键集合均为 `{F5,F6}`，不产生任何输入事件。
- `LAND -> NET` 只发 `F5 up` 与一次 F7；F6 保持；Ctrl/Alt/Shift 按住时阻塞。
- `NET` 中 ring 连续 3 帧 < 0.90（默认退出阈值，0.89 连续 3 帧即触发）：
  只发一次收网 F7；等待动画后回 FIGHT 并补按 F5。未知/失焦/过时/重复帧不算
  低环，不恢复 F5。
- 收网失败/取消：保持 NET + F6 + UNKNOWN fault，不恢复 F5、不重复盲 toggle。
- 中途接管（`net_state=UNKNOWN`）绝不盲 toggle；正常新会话才假定 STOWED。
- 状态 duration/deadline 统一用 `time.monotonic()`。
- UI、日志或截图线程卡住时，状态机 tick 不被阻塞。

## 12. 右侧图形控制面板（已实现）

> 实现文件：`autofish_ui.py`；协议与快照字段以 `autofish_ipc.py` / `autofish_runtime.py`
> 为准。本节保留最初的设计约束，作为评审基线。

### 12.1 独立进程约束（已落实）

UI 不注入 RF4、不改游戏窗口过程，而是一个独立的 Windows 无边框置顶工具窗：

- 用 `GetWindowRect(rf4_x64.exe)` 读取游戏窗口位置（只读）
- 窗口放在 `game_right + 8px, game_top`
- 游戏移动时每 250~500ms 跟随；最小化时隐藏
- UI 崩溃/关闭不影响 bot；bot 崩溃时 UI 显示离线
- UI **绝不直接发送 F5/F6/滚轮**，只通过 IPC 发语义命令

### 12.2 进程关系

```
autofish_ui.py（tkinter/Win32，无边框置顶）
       │  本机 TCP，newline-delimited JSON
       ▼
autofish_runtime.py（状态机主进程）
       ├─ observation（同帧视觉事实）
       ├─ state_machine（状态与迁移）
       ├─ input_arbiter（唯一键鼠 owner）
       └─ friction（档位记账与控制）
```

不用共享文件做实时 IPC：文件适合持久化档位，不适合 250ms 状态更新和命令确认。本机 loopback TCP 足够简单，且 UI/runtime 生命周期天然解耦。

### 12.3 MVP 显示字段

- 连接状态 / bot PID
- 游戏状态：未知、未抛竿、等口、搏鱼、临岸、抄网、结算、弹窗
- 控制模式：自动、仅观察、外部按键占用、手动、故障、正在停止
- 摩擦片：`cur / 29` + 可信度（未知 / 落盘未验证 / 已校准）
- 力度条：1/2/3 档 + 色相
- 线长圆环：百分比 / 不可读
- bot 期望按键 vs 系统观测按键
- 本条鱼耗时、最近一次状态迁移、最近警告

### 12.4 MVP 按钮

| 按钮 | 语义 |
|---|---|
| 启动 | 启动 runtime（先做启动探针，不等于立即发输入） |
| 优雅停止 | runtime 进入 STOPPING，释放 bot 自己持有的键、保存状态后退出 |
| 仅观察 / 自动 | 切 ControlMode，不重启进程 |
| 接管 | 先要求外部 F5/F6 全部松开，再由 bot 接管 |
| 紧急停止 | `taskkill /T /F` + 强制释放；明确标红，可能中断人工输入 |

### 12.5 `bot_ctl.py` 已升级为两级停止

现在的 `stop()` 不再直接 `taskkill /F`：

1. **优雅停止**：IPC `stop` → STOPPING → 停新动作 → `release_owned()` → 保存 → 退出；
   最多等 3 秒，超时只提示用户，不自动强杀。
2. **紧急停止**：显式 `emergency-stop` 才 `taskkill /T /F`，且只对
   `autofish.process.json` 中 pid + 创建时间 + python 镜像 + role 全部可验证的进程执行；
   随后 `release_keys(focus=True)` 强制松键，明确可能干扰人工输入。

没有实例时 `stop()` 绝不调用 `release_keys`（不抢前台、不发 keyUp）。`release_keys()`
的置前行为只保留在紧急/显式释放路径。

### 12.6 MVP 技术选择

优先 `tkinter + ctypes Win32`：项目已有 Python 运行环境，无新依赖；足够实现 320px 右侧工具窗、置顶、跟随、按钮、状态数据。先不做透明 overlay、DLL 注入、游戏内绘制。

### 12.7 UI 上线顺序（已上线）

UI 已作为独立进程实现，只读快照、只发语义命令；关闭 UI 后台继续。上线顺序仍遵守：
先保证状态、输入 owner、计时器和启动初始化，UI 不反向驱动旧的散乱业务代码。
