# 状态机设计（草案 v1，2026-11-04 17:10）

> 状态：**未实现**，仅设计。玩家当前手动上鱼中，本文不含任何输入动作。

## 0. 一句话

把"现在处于哪个阶段"从**代码执行到哪一行**，变成**一个显式、可观测、能从屏幕重新推断的对象**。

## 1. 为什么必须做（今天的事故都能归到三类）

| 事故 | 缺的是什么 |
|---|---|
| 15:48 拉鱼到一半松手，鱼把线拉出 200 米 | 没有"线没收回"这个**状态事实**，只有"计时器到点" |
| 16:47 `ring=-1` 被当成临岸 → 连套 3 次网 → 松手 | "**未知**"没有独立状态，被迫在 是/否 里二选一 |
| 16:15 抄网掏不出来 | 按键**不变量**没有唯一 owner（谁该按住 F5 没人管） |
| 45 秒计时器不重置 | 计时器挂在函数里，跨阶段**泄漏** |
| 重启后"以为 17 实际 29"，顶满断线 | 状态只活在进程内存，**无法从外界重新确认** |
| 每条鱼开头回 17 vs 保留 29 反复摇摆 | 两条代码路径对同一状态各自解释 |

归成三类根因：

1. **计时器 / 计数器没有归属** → 跨阶段泄漏
2. **按键不变量没有唯一 owner** → 谁松的、谁忘了按，查不出来
3. **"未知"被当成确定值** → 把"读不出来"当成"读到了某个值"

状态机不是为了代码漂亮，是为了让这三类 bug **结构性地消失**。

## 3. 启动探针（回答问题 2）

`probe_state()` 采样 3 帧（间隔 0.15s），**按"最确定 → 最不确定"排序**判定：

```
0. 物理按键检查：F5 / F6 已被按下？
     → 是：判定「人工接管中」或「残留按键」
        → 不接管、不产生任何输入，只观察 + 上报
1. 「确定」按钮连续 2 帧成立            → S9_MODAL
2. 入护按钮 / 结算框存在                → S8_SETTLE
3. 鱼图标连续 2 帧存在
     ring >= 0.90                      → S6_LAND
     否则                               → S5_FIGHT
4. bar 有色（level > 0）               → S5_FIGHT
5. ring 可读 或 力度条区域有绘制        → S4_WAIT_BITE
6. 三件套全暗                          → S2_READY（窗口在前台）/ S1_MENU
7. 以上都不成立                         → S0_UNKNOWN
```

铁律：**`S0_UNKNOWN` 与 `S1_MENU` 一律不产生任何键鼠输入**，只打印各判据读数 + 上报截图。宁可不动，不可乱动——今天所有"事故级"问题都发生在"判据不确定却被当成确定"的时刻。

> 判据 3 的"连续 2 帧"是必须的：单帧误读会把 `S4_WAIT_BITE` 误判成 `S5_FIGHT`，一上来就按住左右键（把竿抽回来）。

### 3.1 为什么不"先观察 2 秒再接管"（2026-11-04 17:17）

盲等 2 秒几乎没有额外信息——判据 3 已经要求"连续 2 帧"，本身就在防单帧误判；而"鱼还在不在"这 2 秒能给的信息，用 3 帧采样就已经拿到。

唯一值得单独确认的信息是**这些键现在是不是人按着的**（人在手动搏鱼时脚本再按一次会打架，甚至是 ClickLock 的诱因）。这个不用等，直接探测就够：

```
GetAsyncKeyState(VK_F5 / VK_F6)  →  已按下则判「人工接管中」
```

比盲等更好的做法：**读按键状态 + 比较两帧 bar 值是否在变化**（0.3 秒即可），而不是固定睡 2 秒。

⚠️ 待验证：`GetAsyncKeyState` 能否稳定读到 `pydirectinput`（扫描码 + SendInput）注入的按键。若读不到，退化为"开始接管前先 `keyUp` 一次所有键"这种保守做法，而不是靠观察。

## 4. 分场景初始化（回答问题 3）

### 4.1 核心原则：校准只能朝"安全端"饱和

摩擦片调**小** → 钓具承受力变小 → **不可能断线**；调**大** → 可能直接断线，而且屏幕上没有档位读数可以事后发现。

由此得到一条铁律：

> **任何"档位未知"的时刻，绝对校准只能朝安全端（向下）饱和。**
> 向上饱和（滚满 30 再退回）**只允许在线上无鱼时做**。

这就是你说的"鱼挂着不能 up 30 再 down 13，只能 down 到 0"的本质。它的价值不止是防断线：**向下饱和的结果是确定的**（多滚几格只是无效动作，档位到底就不再变），而向上饱和过一次终点就断线了。

### 4.2 初始化矩阵

| 启动时状态 | 摩擦片初始化 | 其他初始化 |
|---|---|---|
| `S2_READY` | **危险校准**（up 30 → down 13 到 17），线上无鱼，安全 | 复位计时器、清弹窗、抛竿 |
| `S3_CASTING` | 不动 | 等落水 |
| `S4_WAIT_BITE` | **安全校准**（down 30 → up 16 到 17）；线上无鱼但已抛出，没必要冒顶格风险 | 复位计时器、等口 |
| `S5_FIGHT` | **绝不 up 30**。先读力度条：已在 2 档 → **完全不动**；在 1 档 → **down 饱和到 0，再 up 16 到 17**；在 3 档红 → **先降档救急**，校准之后再说 | 按住 F5+F6 |
| `S6_LAND` / `S7_NET` | **不动**（此刻调档无意义，且多一次风险动作） | 按 §7 的临岸流程 |
| `S8_SETTLE` / `S9_MODAL` | 不动，先处理界面 | — |
| `S0_UNKNOWN` | 不动 | 上报 |

### 4.3 "down 到 0 再 up 17" 的落地

操作序列（安全校准）：

```
1. 向下滚 30 格（> 最大档位差，保证到底；多滚只是无效动作）
2. 向上滚 16 格 → 17 档
3. 记账 cur=17, calibrated=True, 落盘
耗时 ≈ 46 格 × 55ms ≈ 2.5 秒
```

**代价**：这 2.5 秒里摩擦一直在低档，鱼会往外跑一点线（不会断线）。可接受，但要尽量少做。

### 4.4 `S5_FIGHT` 初始化：down 饱和 → up 到 17（定稿）

```
1. 向下滚 30 格（保证到底；多滚是无效动作，安全）
2. 向上滚 16 格 → 17 档
3. 记账 cur=17, calibrated=True, 落盘
4. 交给动态控制器（它自己按力度条升降，且受 29 档上限约束）
```

不用"边升边看力度条、到了 2 档就停"那种写法——理由见 §4.5。

### 4.5 数字与色带的分工（2026-11-04 17:17 玩家纠正）

我原先提过"搏鱼时档位数字没有意义，只按力度条闭环往上加"。**这是错的**，玩家指出：

> 如果到了 29 还在往上调，就容易断线了。

两个量各自只能回答一个问题，缺一不可：

| 量 | 能回答 | 不能回答 |
|---|---|---|
| **档位数字**（`_fric["cur"]`） | **还能往上调几格才安全**（29 是硬顶） | 现在负载够不够 |
| **力度条色带** | **该往哪边调、到了没有** | 还能往上调多少 |

- 只有数字没有色带 → 不知道该调多少（早期"永远停在 17"的阶段）
- 只有色带没有数字 → 会一路顶到 30 断线（尤其小鱼、低阻钓组：力度条长期停在 1 档，
  按色带闭环就会无限升档，而这恰恰是之前"档位总爬到 29"的真相）

所以铁律：

> **升档受数字硬约束（≤ 29），升/降的方向与达标由色带判断。**

到 29 且色带仍是 1 档 → **接受现状，不再升**（说明这条鱼/这套钓组的摩阻就这么大，已经到极限）。
这一点写进 `_rise_target()` 的语义里，不改。

## 5. 按键不变量（唯一 owner）

状态机持有 `keys(state) -> set` 的声明式不变量，每次迁移后做一次 reconcile：

```
期望按住集合  vs  当前实际按住集合
  → 多的松开、少的按下；只动差集
```

这直接消灭今天那类 bug（`_both_up` 绕过 `mouse_pressed` 记账、抄网前忘了松 F5）。**没有任何业务代码可以直接按键**，只能改状态。

## 6. 计时器 / 计数器归属状态

| 计时器 | 归属状态 | 生命周期 |
|---|---|---|
| 收线 45s 超时 | `S4_WAIT_BITE` → 进入时创建 | 退出即销毁 |
| 无张力 idle 15s | `S5_FIGHT` | 同上 |
| 临岸宽限 8s | `S6_LAND` | 同上 |
| 抄网重试计数（≤2） | `S7_NET` | 同上 |
| 弹窗连点计数 | `S9_MODAL` | 同上 |

**进入状态时创建、退出时销毁**——45 秒计时器泄漏那类 bug 从结构上不可能再出现。

## 9. 实施顺序（每步可独立回滚）

| 步 | 内容 | 风险 | 收益 |
|---|---|---|---|
| 1 | **只加状态观测**：每 0.2s 推断状态写日志/CSV，控制逻辑一行不改 | 零 | 拿一场真实数据验证判据准不准 |
| 2 | 加启动探针 + `S0_UNKNOWN` 冻结（不产生输入、只上报） | 极低 | 杜绝"判据不确定却动手" |
| 3 | 把 cast/pull/lift 改成状态的 enter/exit，**控制律本体不动** | 中 | 计时器/计数器归属正确 |
| 4 | 按键不变量 reconcile（禁止业务代码直接按键） | 中 | 按键漂移类 bug 消失 |

第 1 步就能验证判据是否靠得住——如果连"当前是不是在搏鱼"都判不稳，后面三步都是空谈。

## 10. 这套东西解决不了什么

- **3D 视角抄网**（走过去对准鱼）——状态机只保证"不确定时不作恶"，不提供新能力
- 断线/重连、小退流程的自动化——需要单独设计
- 网络层佐证（`0e08 fishing/load`）——独立课题
