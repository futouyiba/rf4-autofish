# 弹窗（「确定」框）统一处理

## 为什么需要专门一套

这套客户端在钓鱼流程里会反复弹**需要点「确定」才能继续**的框，而且**排队出现**：

| 弹窗 | 什么时候弹 |
|---|---|
| 获得卡牌（鱼卡） | 入护之后，随机 |
| 获得技能点 / 新技能 | 升级时 |
| 能力解锁（"使用直排(IN-LINE)钓组"、"使用雪人钓组"…） | 技能解锁时，**一次好几个** |
| 升级（"新级别 27"） | 等级提升 |
| 各种提示框 | 随机 |

它们**长得几乎一模一样**，位置也一样。不处理会有两种后果：

1. **抛竿失败**：弹窗吃掉 Shift+F5，变成没有蓄力的短抛（实测事故）
2. **假死**：弹窗盖住 HUD 后，鱼图标恒为 `False`、线长圆环读数为 `-1`，
   等口判据永远不成立，只能一直等到连续 3 轮没口然后重抛

## 实测参数

| 项 | 值 |
|---|---|
| 「确定」按钮边框 | `x871..1048`，`y793..826` |
| 按钮中心 | **(960, 810)** |
| 点击方式 | **必须 SendInput**（`mouse_event` 被客户端丢弃） |
| 连锁层数 | 见过 4 层（升级 → 技能点 → 能力解锁 ×2） |

## 判据

```python
# 按钮在不在：上下两条边框线的亮像素占比都 > 85%
top = a[793, 871:1048]; bot = a[826, 871:1048]
present = (top >= 150).mean() > 0.85 and (bot >= 150).mean() > 0.85
```

连续两帧都成立才算（防单帧闪烁误判）。

## 策略：自己先清，清不掉才上报

```
maybe_dismiss(tag)   ← 统一入口
  ├─ 没有按钮 → 立刻返回（开销约 20ms）
  └─ 有按钮   → 连点到消失（最多 12 次，间隔 0.9s）
        └─ 清完仍有按钮 → 交给上层 / 上报 Agent
```

## 调用位置（四个，覆盖流程所有可能）

| 位置 | 理由 |
|---|---|
| **抛竿前** | 弹窗会吃掉 Shift+F5，导致无蓄力短抛 |
| **等咬钩轮询中**（每 2 秒一次） | 弹窗盖住 HUD 时鱼图标恒 False，会白等到重抛 |
| **入护之后** | 卡牌/技能点弹窗就在这之后弹，且会污染下一轮等口判据 |
| **看门狗兜底**（HUD 15s 不可读） | 万一上面都没接住，这里兜底；清不掉才上报 Agent |

## 与 Agent 接管的分工

- **能自动清的（就是这类「确定」框）** → 脚本自己连点，不打扰人
- **清不掉的**（按钮消失但 HUD 仍不可读 = 不是这类弹窗，比如设置菜单、
  未知界面）→ `agent_hook.escalate()` 上报截图，等 Agent 指令
