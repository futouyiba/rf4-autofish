# 协议状态机与半途接手

视觉判据有**歧义**：圆环读数同时对应好几种状态。实测同一个 0.983 既可能是"刚短抛出去"，
也可能是"鱼被拉到近岸"；0.975 既可能是"入护收回"，也可能是"大鱼贴着岸边"。
用这种连续量去区分 5 个状态，怎么调阈值都是错的。

协议不一样——游戏自己会明确说。

## 1. 事件表（全部实测）

| 类型 | RPC | 方向 | 何时出现 | 性质 |
|---|---|---|---|---|
| `0e01` | fishing/cast_prepare | C2S | 按下蓄力 | 边沿 |
| `0e02` | fishing/cast | C2S | **真正抛出** | 边沿 |
| `0e03` | fishing/fall | C2S | 落水（有时不发） | 边沿 |
| `0e0e` | fishing/bite | S2C | 咬钩 | 边沿（可选） |
| `0e0b` | fishing/hooked | C2S | 中鱼成立 | 边沿 |
| `0e04` | fishing/end | C2S | 战斗结束（空竿/断线也发） | 边沿 |
| `0e05` | fishing/keep_fish | C2S | **只有真上鱼才发** | 边沿 |
| `0e0c` | fishing/left | C2S | 鱼跑了 | 边沿 |
| `0e07` | fishing/step | C2S | **竿在水里时 1 Hz** | **持续态** |
| `0e08` | fishing/load | C2S | **搏斗中每 2 秒** | **持续态** |

> `0e04` **不是**上鱼。上鱼只认 `0e05`。

## 2. 关键区分：边沿 vs 持续

边沿事件错过就没了；**持续态信号可以事后重建**。所以「多久没收到」比「有没有收到过」重要。

| 观测 | 判定 |
|---|---|
| `0e07` 在流 + `0e0b` 晚于最后 `0e02` | `fighting` |
| `0e07` 在流 + 无 `0e0b` | `line_in_water` |
| 有 `0e01` 无 `0e02` | `casting` |
| 持续态停 + 最后边沿 `0e04` | `ended` |
| 持续态停 + 最后边沿 `0e05` | `kept` |
| 持续态停 + 最后边沿 `0e0c` | `fish_left` |
| 什么都没有 | `unknown` → **不许猜** |

**终止边沿优先**：`0e04`/`0e05`/`0e0c` 晚于 `0e0b` 时，即使 `0e08` 还在 3 秒窗口内也不算搏斗
（收鱼时 `0e05` 比 bot 点击晚到，残留的 fighting 会导致立刻重新开战——实机踩过）。

## 3. 半途接手

三种"半途"要分清：

| 情况 | 能不能救 |
|---|---|
| 抓包器晚于 TCP 连接建立才启动 | **不能**。RC4 流密码必须从握手开始，整条连接永久不可解 |
| 抓包器在跑，bot 中途启动/重启 | **能**，读 `_sniff/state.json` 按 phase 接手 |
| 游戏断线重连 / 重启 | 新连接=新握手，能解；**token 会换**，抓包器自动重新握手 |

### 动作表（`autofish_handoff.resolve()`）

| phase | 进入状态 | 按键 | 理由 |
|---|---|---|---|
| `fighting` | FIGHT | **不动键** | 搏斗中松 F5/F6 会跑鱼 |
| `line_in_water` | WAIT_BITE | 松键 | 竿在水里 |
| `casting` | PROBING | **短按 F5 0.25s 再松** | 蓄力中追加后释放，确保抛出而不是无限蓄力 |
| `kept` | PROBING | 松键 | `0e05` 确认上鱼 |
| `ended` / `fish_left` | PROBING | 松键 | 重新抛 |
| `unknown` / 快照 >10s / 事件 >60s | PROBING | 松键 | **不猜**，回视觉判据 |

### 安全边界

* **FIGHT 接手不绕过档位防线**：`friction_untrusted` 时首帧 FAULT，交人工；
* **快照新鲜度**：`state.json` 每事件更新 + 每 5s 兜底刷新，读时 >10s 视为无效；
* **存活判据取三者最小**（`event_age` / `step_age` / `load_age`）——搏斗中 `0e07` 可能停，
  只有 `0e08` 在流，单看 `event_age` 会误判陈旧；
* **协议否决环判据**（2026-11-09 实机踩过的三处死锁）：

  | 位置 | 环怎么说 | 协议怎么说 | 以谁为准 |
  |---|---|---|---|
  | `retrieve` 的 .98 兜底 | 满环 = 收完 | `0e07` 在流 = 还在水里 | **协议**，继续收线 |
  | `retrieve` 开头的 `_line_on_spool` | 满环 = 不用收 | `0e07` 在流 = 要收 | **协议**，按 F5 收 |
  | `WAIT_BITE` 的 `line_home` | 满环 = 线在杯上 | `0e07` 在流 = 在等口 | **协议**，继续等 |

  根因是短抛后环也读 1.0，只有 `0e07` 能区分"线在水里"和"线在杯上"。
* **离开搏斗/收完线后 4 秒静默期**：期间不采信任何协议判据，防止入护后空打、
  收完线又被拉回等口；
* **抓包器没跑** → 协议回调返回 `None`，视觉判据照常工作（协议只是补充）。

## 4.5 抓包器不能被打断

`state.json` 是 bot 与抓包器的唯一接口，bot 会 0.5s 轮询一次。Windows 上
`os.replace` 偶尔会撞上读取方的共享锁——**这个异常绝不能抛出去**，否则会打断
scapy 的抓包线程（实测：bot 开始轮询后抓包器静默死掉、事件停在几百秒前）。
现在 `_atomic_write` 失败重试 4 次后放弃本次快照，`handle()` 整体也包了异常兜底。

## 4. 补盲区：咬钩图标不亮

鱼贴到岸边或图标被 UI 遮住时 `fish_icon=false`，但 `0e0b`/`0e08` 仍在流。
2026-11-09 实测：协议 `bout_elapsed=32.9s`、`line_out=7.86m`，而 bot 停在 `WAIT_BITE`
白白等到超时。现在 `PROBING` / `WAIT_BITE` 都会在视觉确认之前先问一次协议，
命中就走 `_begin_fight("protocol_fight")`。

## 5. `0e08` 的 float（搏鱼/物理分析）

DTO21，27 个 float，从魔数 `01 15 00 00 00` 之后开始读。实测校准：

| 索引 | 含义 | 实测样例 |
|---|---|---|
| 3 | 本场搏斗已经过秒数 | 0.0 → 0.749 → 5.768 → 10.015 → 13.98 |
| 9 | 力/速度类变化量 | 0.79 → 0.152 → 0.104 |
| 19 | 当前放线长度（米） | 8.80 → 8.74 → 9.05 → 7.85 |
| 20 | 与 `0e02` 的 `line_out_length` 同值 | 15.738 → 12.991 → 8.561 |
| 25 | 会话时钟（秒） | 187.214 → 189.216（+2.002s） |

全部写入 `_sniff/events.jsonl` 的 `f` 字段，可直接拉出受力-放线曲线。

## 6. 产物与启动顺序

```
bot/_sniff/events.jsonl   全量事件（含 0e08 float），事后对齐/回放
bot/_sniff/state.json     状态快照（phase / beat 年龄 / bout_elapsed / line_out）
```

**顺序铁律：抓包器 → 登录器 → 游戏**。抓包器必须先于游戏连接启动，否则拿不到 RC4 token。

```bash
# 先起抓包器（系统 python，有 scapy + Npcap）
python rf4_sniff.py --quiet >> _sniff/sniff.log 2>&1 &
# 再启动游戏登录器
```

抓包器挂了不影响 bot 运行，但协议判据全部失效，日志里会看到 `no_protocol_snapshot`。
